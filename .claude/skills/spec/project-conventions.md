# Spec Project Conventions — Rust Project

This file is this project's conventions for the `/spec-*` workflows: every `/spec-*` workflow reads it at startup and follows it. It is yours to edit. It started from the spec-workflows Rust project template, which `mcp-planner setup` installs under `purpose = "ywata-rust-project"`; that is why a later update of the template can arrive beside it as a staged `.project-conventions.incoming.md`.

It is customized for this crate, `mcp-tools` (repository `mcp-sexpr`): the spec-id prefix is `mcp-tools`, the paths below are this repository's, and archiving is a separate, user-run step (§ Lifecycle Transitions). When setup reports a merge pending for this file, run `/merge-customizations`; commit `project-conventions.md` together with `.project-conventions.default.md`.

## Spec-Id Conventions
<!-- section: spec-id-conventions -->

**Active**: yes — all spec files in this project use `<!-- spec-id: ... -->` annotations.

### Format

```
mcp-tools/<category>/<item>[/<subitem>...]
```

- Lowercase, kebab-case, ASCII only.
- At least 2 slashes (minimum 3 components).
- Stable across refactoring — do not change unless the concept itself changes.

### Placement Rules

- Add `<!-- spec-id: ... -->` immediately after every **second-level heading (`##`)**.
- A `###` subsection **may additionally** get its own **claim-level** spec-id when it is a *distinct, stable, independently-testable claim* on a high-value surface (API behavior, validation, error handling). Split a `##` into claim-level `###` ids when it bundles ≥3 such claims and you want per-claim coverage tracking. Introduce these **opportunistically** — only when a doc is already being revised for a spec change, or when explicitly asked — never as a bulk retrofit, and add the per-claim tests in the same change so coverage does not dip. When you decompose a `##` this way, mark the `##` umbrella `non-testable` (its testable content now lives in the child claims).
- **Track consideration status.** When you review a `##` section and deliberately keep it coarse, add `<!-- granularity: reviewed YYYY-MM-DD -->` under its spec-id. A helper script (e.g. `bin/granularity_status.sh`) can list testable-coarse-unmarked sections (the outstanding work-list). Re-date/remove the marker on material revision; visibility informs opportunistic work, it does not mandate a retrofit.
- Other third-level headings (`###`) and below (examples, details, rationale) do **not** need spec-ids.
- Mark non-testable sections with the `non-testable` flag:
  ```markdown
  ## Design Rationale
  <!-- spec-id: mcp-tools/design/rationale non-testable -->
  ```

### Non-Testable Classification

Use `non-testable` for: design rationale, references, future enhancements, background, overview sections.

Do **not** use `non-testable` for: API behavior, data formats, algorithms, validation rules, error handling.

### Examples

```markdown
## Register Plan
<!-- spec-id: mcp-tools/api-spec/register-plan -->

## Design Rationale
<!-- spec-id: mcp-tools/design/rationale non-testable -->
```

### After Spec Changes

Run `cargo build` after any spec-id changes to regenerate the traceability code and the `SpecItem` enum (generated by `build.rs` using `spec-files.txt`).

## Spec-Trace Conventions
<!-- section: spec-trace-conventions -->

**Active**: yes — this project uses the `spec-trace` CLI tool.

### Coverage Recording vs Compile-Time Traceability

spec-trace serves two related but different purposes:

- **Compile-time traceability**: `SpecItem` enum variants referenced from tests ensure spec-ids exist.
- **Runtime coverage recording (SQLite)**: tests record which `SpecItem` values were covered into a SQLite database when `SPEC_TRACE_DB` is set.

Coverage reporting scripts rely on runtime coverage recording.

If a project defines its own `covers!()` macro that only references `SpecItem` (e.g. `let _ = SpecItem::...;`), it provides compile-time traceability but it will not create a coverage database and the coverage script will not work.

### Downstream Project Checklist (DB-based Coverage)

For projects that want `SPEC_TRACE_DB` + SQLite coverage reporting:

1. Add `spec-trace` as both `[build-dependencies]` (for codegen) and `[dependencies]` (for runtime coverage + macro).
2. Maintain `spec-files.txt` as the shared source of truth for spec docs.
3. Run `cargo build` after spec changes to regenerate the traceability code.
4. Ensure tests use `spec_trace::covers` (directly or via a re-export) so coverage events are recorded.
5. Run tests with `SPEC_TRACE_DB=coverage.db cargo test` before running the coverage report.

### Available Subcommands

- `spec-trace check-links --dirs specs/` — validate cross-references in spec files
- `spec-trace check-links --dirs specs/ --output-index link-index.toml` — also write resolved link map
- `spec-trace rename --mapping spec-rename.toml --index link-index.toml` — dry-run rename
- `spec-trace rename --mapping spec-rename.toml --index link-index.toml --apply` — apply rename

### `spec-files.txt`

**Active**: yes — `spec-files.txt` at the repository root is the shared source of truth for `build.rs` and coverage scripts.

- Add new spec file paths when spec files are created.
- Remove paths when spec files are deleted or archived.
- Updated during plan execution (`/exec-plan`), not during proposal (`/spec-change`).
- **NEVER add change specs (`specs/changes/`) to `spec-files.txt`.** Only permanent spec files belong here. Change spec spec-ids are documentation only — they don't enter the build system.

### Spec-Id Ordering in Plans

When a change spec plan introduces new testable spec-ids:

- **Spec-creation goals must precede test goals** for the same spec-ids. Any goal that writes `covers!([SpecItem::X])` requires that spec-id `X` already exists in a permanent spec file listed in `spec-files.txt`.
- New spec-ids proposed in the change spec's `new-spec-ids` metadata must be added to permanent spec files during implementation (as part of spec-creation goals), not deferred to plan completion.
- At plan `all-complete`, the exec-plan workflow verifies all proposed spec-ids exist in permanent specs — this is a check, not the time to create them.

### Reorganization Pattern (Sandwich)

Before any rename: validate → rename → validate → rebuild.

```bash
git status                                                          # must be clean
spec-trace check-links --dirs specs/ --output-index link-index.toml
spec-trace rename --mapping spec-rename.toml --index link-index.toml        # dry-run
spec-trace rename --mapping spec-rename.toml --index link-index.toml --apply
spec-trace check-links --dirs specs/
cargo build && cargo test
```

Rollback: `git checkout HEAD -- . && git clean -fd`

### Coverage Script Assumptions

The coverage script `bin/check_coverage.sh` assumes:

- The repo root contains `spec-files.txt`.
- Tests are executed with `SPEC_TRACE_DB=coverage.db`.
- The `spec-trace` CLI is installed, pinned to the rev this project's `Cargo.lock` names (see `docs/spec-trace-guide.md`).
- The script runs `spec-trace run --threshold <this project's threshold>`; the threshold is set in the script only.

### Mapping File Format

```toml
[[moves]]
old = "specs/api/claim-goal.md"
new = "specs/api/planner/claim-goal.md"
old_prefix = "mcp-tools/api/claim-goal"
new_prefix = "mcp-tools/api/planner/claim-goal"
```

### Note for `/spec-analyze`

When proposing reorganizations, note which changes would require `spec-trace rename`. Do **not** invoke spec-trace directly — advise the user to run it.

## Change-Spec Lifecycle
<!-- section: change-spec-lifecycle -->

**Active**: yes — change specs in this project use the full lifecycle metadata.

### File Naming Convention

Change spec files in `specs/changes/` follow the pattern:

```
DATESTAMP-NAME.md
```

- `DATESTAMP` is the creation date in `YYYY-MM-DD` format.
- `NAME` is a short kebab-case description of the change.
- Do **not** append `-change-spec` or `-spec` to the filename. The `specs/changes/` location already conveys that the file is a change spec.
- The associated goal tree file uses the same name with `.scm` extension: `DATESTAMP-NAME.scm`.

Examples:
- `specs/changes/<date>-<topic>.md` → `specs/changes/<date>-<topic>.scm`

### Metadata Fields

Place the `## Change Metadata` section at the top of the file, immediately after the title and header fields (Date, Status, Type, Impact, Supersedes), before all content sections.

| Field | Description |
|---|---|
| `Status` | `proposed` → `in-progress` → `completed` |
| `plan-file` | Path to associated `.scm` goal tree (set during `/make-plan`) |
| `updates` | Existing spec files being updated |
| `adds` | New spec files being added |
| `obsoletes` | Spec files being removed |
| `merge-into` | Target file if merging content |
| `new-spec-ids` | New spec-ids introduced by this change |
| `modified-spec-ids` | Existing spec-ids modified |
| `retired-spec-ids` | Spec-ids being removed |
| `non-testable-sections` | Spec-ids in this change that are non-testable |
| `consumer-notice` | Who this change must tell, and how they were told — see § Consumer Notice. Never blank |

### Consumer Notice

`consumer-notice` carries exactly one of:

- **the parties who must act**, each with the message id (or other reference) by which they were told;
- **a reference alone**, when they were told while the work was still in flight;
- **`(none)` with a reason**, when no notice is owed.

The row is never blank and never omitted. It is settled **before the archive**.

Notice is owed when a consumer must **do** something, or when something they already wrote stops being correct — not merely because they will receive different bytes. When it is unclear, write the sentence you would send: if it reads "we changed X, you need do nothing", no notice is owed and that sentence is the reason; if it reads "we changed X, run Y" or "… so your Z is now wrong", it is owed.

### Lifecycle Transitions

- `/spec-change` sets `Status: proposed`, `plan-file: (none)`.
- `/make-plan` sets `Status: in-progress`, sets `plan-file:` to the generated `.scm` path.
- `/exec-plan` sets `Status: completed` when all goals finish.
- A commit that finalizes a change spec's work also sets `Status: completed` (for work completed outside `/exec-plan`).
- `consumer-notice` is settled before archiving: any notice still owed is sent, and the row records it.
- `/spec-change-archive` moves completed `.md` + `.scm` to `specs/changes/archive/`. **Archiving is a separate, user-run step**: it runs only when the maintainer says so, never as part of completion. It stops while any tracked file outside `specs/changes/` still refers to a file being archived by path; cite a change spec by title, date and completing commit instead.

### Spec-Id Classification in Change Specs

For each spec-id in `new-spec-ids`, classify as testable or non-testable. List all non-testable ones in `non-testable-sections`. Ensure `<!-- spec-id: ... non-testable -->` annotations in the change spec body are consistent with this list.
